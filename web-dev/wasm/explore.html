WebAssembly Runtime Model

What's actually in a .wasm file, and what happens when you run it

WebAssembly is a binary instruction format — a portable compilation target that runs in browsers and on servers. But "compilation target" undersells it. WASM defines a runtime model: a sandboxed stack machine with linear memory, no direct access to the outside world, and a strict boundary between host and guest.

You can read the spec, or you can poke at it. Let's poke.

Below is a complete, valid WASM module — hand-assembled, byte by byte. It contains a single function: add(a, b) -> a + b. Hover over the bytes to see what each one does.

This is 41 bytes. The entire module. No runtime, no garbage collector, no standard library. Just the function, the types, and the export. That's the WASM value proposition: it's exactly what you asked for, nothing more.
Now you've seen what's inside. But 41 bytes of pure logic can't do anything useful alone...

WASM is a guest in someone else's house. The host decides what the guest can do. In a browser, the host is JavaScript. On Cloudflare, the host is the Workers runtime. Same WASM module, different capabilities — because the imports are different.
So WASM needs a host. But is it worth the trouble? When is WASM actually faster?

Sandbox 4: The Language Tax

The same trivial add(a, b) function — compiled from different languages. The difference in binary size tells you what each language brings along: runtime, GC, allocator, standard library stubs. Click a row to see what's in the binary.

The "language tax" is everything your compiler adds beyond your actual code. For a trivial function, the tax is the binary. For a real application, the tax becomes a smaller fraction — but it determines your floor. Go's 2.5MB floor makes it impractical for small WASM modules. TinyGo and Rust (no_std) sit in the sweet spot.

Sandbox 5: Threading — SharedArrayBuffer + Web Workers

WASM has no spawn_thread instruction. Threading comes from the browser: you create Web Workers, give them a SharedArrayBuffer, and use WASM's atomic operations to coordinate. It's pthreads semantics — shared mutable memory with atomics — not goroutines or Erlang processes.

The Catch: HTTP Headers Required

After Spectre/Meltdown, browsers disabled SharedArrayBuffer unless the page sends: 

Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp

Without these headers, SharedArrayBuffer is undefined. Our local dev server doesn't send them, so this demo simulates the threading model using the main thread with the same WASM atomic instructions — the operations are real, the parallelism is illustrated.

Language Support

Language Thread Support Notes
C/C++ (Emscripten) ✓ Full -pthread flag auto-generates Worker scaffolding
Rust (wasm-bindgen) ● Experimental wasm-bindgen-rayon crate; works but rough edges
Go ✗ None Goroutine scheduler assumes single-threaded WASM
TinyGo ✗ None Same limitation — no shared memory threading
Odin ● Possible WASM target is experimental; atomics in principle but untested
WASM threading is real but low-level: it's shared memory with atomics, orchestrated by JavaScript Web Workers. The browser owns the threading model, WASM provides the atomic instructions. C/C++ via Emscripten is the best-supported path. Go's goroutines don't translate — the scheduler can't spawn real OS threads in the browser. For most WASM use cases, single-threaded is fine. Threading matters for compute-heavy workloads: image processing, physics simulations, codecs — the same things that justify WASM in the first place.
