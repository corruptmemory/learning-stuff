WASM on the Edge: Cloudflare Workers

Why you'd run WebAssembly on a server, and when it makes sense

WebAssembly was designed for the browser. Then people realized: the same properties that make it good for browsers — sandboxing, near-native speed, language-agnostic — make it interesting for servers too. Cloudflare Workers run your code at the edge, in V8 isolates, and they can run WASM. The question isn't whether you can — it's whether you should.

Workers don't use containers. They use V8 isolates — lightweight execution contexts within a single V8 process. A single machine can run thousands of isolates. WASM modules load inside these isolates. The cold start is V8's isolate creation, not your module's compilation (that's AOT-cached by Cloudflare).
So Workers are fast to start and cheap to run. But where they run is the real differentiator...

Sandbox 2: The Edge — Geography as Architecture

Pick a user location and see how latency changes across three deployment strategies. The computation is identical — only the network distance differs.

The "edge" isn't about computation speed — it's about proximity. A Worker running at the edge is physically closer to the user. The computation is identical to what you'd run in us-east-1, but the network round-trip is shorter. This matters most for: latency-sensitive APIs, real-time features, and globally distributed users.
Geography helps with latency. But not every workload benefits from being at the edge...
