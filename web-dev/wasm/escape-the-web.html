Can I Just WASM a Frontend?

The honest answer to "do I need JavaScript?"

You know a systems language. You hate JavaScript. WebAssembly exists. The question is obvious: can you skip the entire web frontend stack and just... write your UI in a real language? The answer is nuanced, and depends on what you mean by "frontend."

Sandbox 1: What You Need From the Browser

Before you can replace JavaScript, you need to know what it actually does. Here's what the browser provides — and whether WASM can touch it directly. Click any row to see why.

The DOM is the browser's API. WASM can't bypass it. If you want text, forms, and layout — you're either writing JS glue or using a framework that writes it for you. If you want pixels on a canvas — you can mostly stay in WASM land.
So WASM can't touch the browser directly. But there are different strategies for bridging the gap...

Sandbox 2: The Spectrum

Three strategies for building a web frontend with WASM, from "mostly JS" to "almost no JS." Each trades different things.

Mostly JS

Thin Glue

Business logic in WASM, UI in HTML/JS. JavaScript handles all DOM, events, and rendering. WASM does the heavy lifting: validation, crypto, data processing, simulation.
You gain
Full browser API access, small WASM binary, easy debugging, progressive enhancement
You give up
Nothing — but you still write JS for the UI
WASM: ~1-50 KB
Hybrid

Canvas Only

No DOM elements except the <canvas> itself. WASM handles all rendering via WebGL/Canvas2D. JS is just a thin event-forwarding shim (~20 lines). Games, data viz, creative tools.
You gain
Almost no JS to write, full control over rendering, port native engines directly
You give up
Text selection, accessibility, browser dev tools for layout, scrolling, form controls
WASM: 50 KB - 5 MB
Mostly WASM

Virtual DOM Framework

Rust: Yew, Leptos, Dioxus. Go: Vecty (abandoned), Vugu. The framework maintains a virtual DOM, diffs it, and calls JS to patch the real DOM. You write "HTML-like" code in your language.
You gain
Write UI in your language, type safety, component model, familiar SPA patterns
You give up
Large binary (framework + runtime), slower DOM updates than native JS, smaller ecosystem
WASM: 200 KB - 5 MB
There's no escape from the browser's API — only different ways to talk to it. The question isn't "can I avoid JS entirely?" (you can't, except on canvas). The question is "how much JS do I have to write myself?"
The canvas approach is the most "pure WASM" option. Let's see it in action...

Sandbox 3: The Canvas Escape Hatch

A live demo of the canvas-only approach. The "WASM module" owns all state and logic — position, velocity, color computation, collision detection. JavaScript does exactly two things: forward mouse events and call Canvas2D draw methods. Move your mouse over the canvas.

WASM state: x=450 y=200 r=30 | color: rgb(100, 100, 200) | mouse: (-, -)
The entire JS shim (~25 lines)
// This is all the JavaScript you need. It never changes. // Your application logic lives in the WASM module. const canvas = document.getElementById('demo-canvas'); const ctx = canvas.getContext('2d'); let mouseX = -1, mouseY = -1; canvas.addEventListener('mousemove', e => { const rect = canvas.getBoundingClientRect(); mouseX = (e.clientX - rect.left) * (canvas.width / rect.width); mouseY = (e.clientY - rect.top) * (canvas.height / rect.height); }); canvas.addEventListener('mouseleave', () => { mouseX = -1; mouseY = -1; }); let lastTime = performance.now(); function frame(now) { const dt = (now - lastTime) / 1000; lastTime = now; wasm.update(mouseX, mouseY, dt); // WASM owns state + logic // JS does I/O: read state, draw pixels ctx.clearRect(0, 0, canvas.width, canvas.height); ctx.beginPath(); ctx.arc(wasm.getX(), wasm.getY(), wasm.getRadius(), 0, Math.PI * 2); ctx.fillStyle = `rgb(${wasm.getR()},${wasm.getG()},${wasm.getB()})`; ctx.fill(); requestAnimationFrame(frame); } requestAnimationFrame(frame);
The canvas escape hatch is real. If your UI is "pixels on screen" — games, visualizations, creative tools — you can write almost everything in your preferred language. The JS shim is boilerplate that never changes. But you lose everything the browser gives you for free: text rendering, accessibility, scrolling, form controls, dev tools.

Sandbox 4: The Verdict

An interactive decision tree. Click your answer to each question.

The honest answer: WASM can replace JavaScript for canvas-based UIs today. For DOM-based UIs, it adds complexity without removing JavaScript — it just hides it behind a framework. The pragmatic middle ground is often: server-side language you love + HTMX, with WASM modules for computationally heavy client-side work.
