React: Why Crazy People Use It

What it actually does, how it works, and whether you need it

React is the most popular frontend framework in the world. That doesn't make it good — it makes it worth understanding. This exploration will show you what problem React solves, how it works under the hood, and when it's the right (or wrong) tool. No prior React knowledge assumed.

Sandbox 1: The Problem React Solves

Two implementations of the same widget: a filterable, sortable table. The left uses vanilla DOM manipulation — the way a competent developer would build it without a framework. The right uses React. They look and behave identically. Watch the DOM operation counters.

The vanilla JS version works. It's not even bad code — it's the natural way to build this without a framework. But every user interaction triggers a full rebuild of the table body. The React version rebuilds a virtual representation, diffs it against the current one, and only touches the DOM nodes that actually changed. For 10 rows, this barely matters. For 1000 rows, it's the difference between smooth and janky.
Now you've seen what React does differently. But how does this "virtual DOM diffing" actually work?

Sandbox 2: The Virtual DOM — What's Actually Happening

React builds a tree of plain JavaScript objects — the virtual DOM — that mirrors the real DOM. When state changes, React builds a new tree, walks both trees top-down, and computes the minimal set of DOM mutations. This is the reconciliation algorithm. Watch it work.

React's reconciliation is $O(n)$ — it walks both trees top-down, comparing node by node. The optimal tree diff algorithm is $O(n^3)$, which is unusable for real UIs. React's heuristic: (1) different element types produce different trees — don't bother diffing children, just replace. (2) The key prop tells React which children moved vs. which were added/removed. Without keys, a reorder looks like every item changed. With keys, React sees the move and does one DOM operation instead of $N$.
