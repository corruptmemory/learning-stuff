React: Why Crazy People Use It

What it actually does, how it works, and whether you need it

React is the most popular frontend framework in the world. That doesn't make it good — it makes it worth understanding. This exploration will show you what problem React solves, how it works under the hood, and when it's the right (or wrong) tool. No prior React knowledge assumed.

Sandbox 1: The Problem React Solves

Two implementations of the same widget: a filterable, sortable table. The left uses vanilla DOM manipulation — the way a competent developer would build it without a framework. The right uses React. They look and behave identically. Watch the DOM operation counters.

The vanilla JS version works. It's not even bad code — it's the natural way to build this without a framework. But every user interaction triggers a full rebuild of the table body. The React version rebuilds a virtual representation, diffs it against the current one, and only touches the DOM nodes that actually changed. For 10 rows, this barely matters. For 1000 rows, it's the difference between smooth and janky.
Now you've seen what React does differently. But how does this "virtual DOM diffing" actually work?

Sandbox 2: The Virtual DOM — What's Actually Happening

React builds a tree of plain JavaScript objects — the virtual DOM — that mirrors the real DOM. When state changes, React builds a new tree, walks both trees top-down, and computes the minimal set of DOM mutations. This is the reconciliation algorithm. Watch it work.

React's reconciliation is $O(n)$ — it walks both trees top-down, comparing node by node. The optimal tree diff algorithm is $O(n^3)$, which is unusable for real UIs. React's heuristic: (1) different element types produce different trees — don't bother diffing children, just replace. (2) The key prop tells React which children moved vs. which were added/removed. Without keys, a reorder looks like every item changed. With keys, React sees the move and does one DOM operation instead of $N$.
You've seen the virtual DOM and reconciliation. Now: what triggers a re-render, and what happens inside the component when it runs?

Sandbox 3: useState, useEffect, and the Render Cycle

A React component is a function. Every time state changes, React calls that function again. There is no object, no instance variable, no this.state. Hooks like useState and useEffect are how a plain function gets memory and side effects. The "magic" is an array.

useState: It's Just an Array

React maintains a hidden array of hook values for each component. useState(0) reads from index 0. A second useState("hello") reads from index 1. The index is determined by call order — which is why hooks can never be called conditionally.

useEffect: Side Effects After Paint

Effects run after the browser paints. They're for things that don't belong in the render itself: fetching data, subscribing to events, setting timers. The dependency array controls when they re-run.

useEffect(() => { // runs once }, [])
Mount only. Empty deps = run once after first paint. The setup function for a subscription, a fetch, a DOM measurement.
useEffect(() => { // runs when count changes }, [count])
On dependency change. Runs after first paint, then again whenever count changes. React compares deps with Object.is().
useEffect(() => { subscribe(); return () => unsubscribe(); }, [])
Cleanup on unmount. The returned function runs when the component is removed from the DOM. Prevents memory leaks.

The Stale Closure Gotcha

Every render is a function call. Every function call creates a closure. That closure captures the state values as they were during that render. If you stash a function (like a setTimeout callback), it holds onto the old values forever.

Try it: Click "Capture in setTimeout", then rapidly increment the counter 5 times. After 3 seconds, the timeout fires — and logs the old value.

React components are just functions. Every render is a function call with a snapshot of the current state. useState is an array index. useEffect is a callback that runs after paint. The "magic" is bookkeeping — React tracks which component is rendering, which hook index you're on, and which effects need to run. There is no magic.

Decision Tree
Given your stack (Go + templ + HTMX) React adds a build step, a virtual DOM, and a JavaScript-heavy client to a stack that already works. The only scenario where React makes sense for you is if you're building something with heavy client-side interactivity — a code editor, a real-time dashboard, a drawing tool. For most web applications, you already have the better tool.
React is excellent at what it was designed for: complex, stateful, interactive UIs where the server is just an API. If that's not your app, React is overhead. The JavaScript ecosystem will tell you everything needs React. Most things don't.
